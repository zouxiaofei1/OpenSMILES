**任务**: 按照文中架构和计划写NamePredict API，其最终目标: 高准确率，10ms以下的SMILES转中英文API
**重要教训**: 不要写基团取代型预测代码，需要系统性实现命名逻辑

**方法约束**: 不得使用深度学习模型，不得全部使用缓存系统，只能缓存俗名和例外，目前最多缓存**100**个

#工作步骤：
0. 读取 workstate.md，了解当前进度和计划。
0.1 workstate.md中## 其他 行的行号如果尾数为偶数，当前工作轮次为架构改进轮；可以使用 skills/analyzing-architecture-risk 分析项目风险；如果程序速度较慢，如benchmark耗时超过30s,则无论何轮次，优化程序性能。跳到3.
1. 运行**benchmark**,记录并报告当前分数，格式**中英文双重准确:[ ]%**
2. 如果workstate的其他中没有选题，使用错误驱动方式进行选题。否则进行工作。
选题流程:
2.0当选题需要，大概要修改某一layer时，务必阅读wiki（和layer，架构相关）,目录docs\wiki。根据wiki中的信息考虑，这一选题是否适应合适。
2.1.从benchmark数据库中随机选一个错的分子，选中后不要换题目。
2.2.现在命名情况如何?是否能一轮修好?
2.3 如果完全fail/坍缩/母体错且分子复杂，尝试命中母体
2.4 如果核心正确，且取代基未命名完全，尝试命名全取代基。
2.5 如果取代基很复杂，一次无法命名完全，可以做基础设施，命名其中的一部分。
2.6 如果较为简单，则一次完全命名。

3. 调用一个subagent,进行编写代码（遵守 skills/chem-tdd-skill）
4. 调用另一个subagent（review）：**必须先阅读并全文遵守 skills/chem-code-review**。
   - 先审**选题**再审代码：代码全绿也可以反对选题；裁决 PASS|FIX|ROLLBACK|CHALLENGE
   - 每个方法不得超过10行，超限则拆分；不应有架构性问题；输出审查报告
4.1. review 运行**benchmark**（有 diff 时），分数回退不得>0.5%,否则 ROLLBACK（见 chem-code-review）
4.2. **共识环**（直到选题一致，一致前禁止 git 提交）:
   - CHALLENGE → 主 Agent 书面回应（接受替代选题 / 辩护原题须给 dual 与通用化理由 / 折中粒度）→ 再调用 review
   - FIX → 按「必须修改」改代码 → 再 review
   - ROLLBACK → 回滚工作区 → 重新选题或换方案 → 再进入 3–4
   - 往返≥3 轮仍无交集 → 暂停交人类，不得 commit
6. 仅当 review **PASS**（选题同意且代码合格）后 git提交
7. 在开发日志(workstate.md)中按照格式记录更改。
8. 暂停，报告更改，每次只处理一个问题

##编码规范与设计经验
1.constants.py存在常量如(原子序数，倍数前缀等)，避免硬编码。
2.文件大小应该在50-500行之间。特殊情况下可以更大或更小
3.layer2和layer3是互相确定的，有互相调用正常，但是layer2不应包含取代基选择，layer3不应包含母体选择逻辑
4.如果反复修改分数却不增加，往往是架构不对。
5.在处理一层的代码时，想象其他层是完美的
6.常见失败模式:空返回,结构错误，母体选错，侧链选错，编号错，缺功能
7.benchmark一般elapsed<10s,成本很低，多运行防止回归。如果耗时明显增加，估计是代码有问题。
8.层间可以互相调用，只要不逻辑混乱，不循环引用即可
